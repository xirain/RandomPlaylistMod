1 需求概述

1.1 核心目标

编号目标说明
G1游玩记录持久化每次会话结束后，自动保存完整的游玩数据到本地 JSON 文件
G2运动数据追踪记录每首歌的得分、连击、失误、精度等运动表现数据
G3分享功能支持将会话摘要生成图文内容，用于游戏内分享和外部社交平台分享
G4本地存储数据保存在 Beat Saber 游戏目录下的独立文件夹，不依赖外部服务

1.2 非功能需求

  • 可靠性：数据写入失败不影响游戏正常运行，采用 try-catch 保护
  • 兼容性：JSON 格式向下兼容，新增字段使用默认值
  • 性能：写入操作在会话结束时异步执行，不阻塞主线程
  • 隐私：所有数据仅存储在本地，不上传到任何服务器

1.3 用户故事

#角色场景价值
1玩家 完成一次 60 分钟随机歌单会话后，我希望看到这次打了哪些歌、得了多少分 成就感、复盘
2玩家 想回顾上周的运动数据，看看进步了多少 运动追踪、进度可视化
3玩家 完成一次精彩的会话后，想把总结分享到小红书/B站 社交分享、引流
4开发者 需要知道用户实际使用中遇到的问题，看会话日志排查 调试、优化

2 数据模型设计

2.1 新增模型总览

模型类文件说明存储
SessionRecordModels/SessionRecord.cs单次会话完整记录History/{guid}.json
SongResultModels/SongResult.cs单首歌曲的游戏结果嵌入 SessionRecord
PlayerProfileModels/PlayerProfile.cs玩家聚合统计数据profile.json
ExerciseSummaryModels/ExerciseSummary.cs单次会话的运动汇总嵌入 SessionRecord
设计原则：采用「一 Session 一文件」策略，每个 SessionRecord 独立存储为一个 JSON 文件。 这样读取历史列表时只需扫描文件夹，无需解析大型文件。PlayerProfile 作为聚合缓存单独存储。

2.2 SessionRecord — 会话记录

最核心的数据模型，记录一次随机歌单会话的完整信息。

字段类型必填说明
SessionIdstring (GUID)✅唯一会话标识，格式 20260623-143052-a1b2c3d4
StartedAtDateTime✅会话开始时间（本地时间 ISO 8601）
EndedAtDateTime✅会话结束时间
TargetDurationMinint✅目标时长（分钟）
ActualDurationMinint✅实际时长（分钟，四舍五入）
PlaylistIdsList<string>✅选中的播放列表 ID 列表
PlaylistNamesList<string>✅选中的播放列表名称列表（用于分享展示）
TotalSongsInQueueint✅队列中的总歌曲数
TotalSongsPlayedint✅实际播放的歌曲数
SongResultsList<SongResult>✅每首歌的详细结果（按播放顺序）
ExerciseSummaryExerciseSummary✅本次会话的运动数据汇总
SettingsSessionSettingsSnapshot✅本次使用的设置快照（NPS范围/BPM/NoFail等）
TagsList<string>❌用户自定义标签（后续可扩展）

2.3 SongResult — 歌曲结果

记录单首歌曲的游戏表现。数据来源：Beat Saber 的 LevelCompletionResults。

字段类型必填说明
SongNamestring✅歌曲名称
Authorstring✅作者/艺术家
LevelIdstring✅关卡 ID
Difficultystring✅难度名称（Expert+/Expert/Hard/Normal/Easy）
Scoreint✅总得分
MaxScoreint✅理论最高分
Rankstring✅评级（SS/S/A/B/C/D/E）
MaxComboint✅最大连击数
MissedNotesint✅失误次数
BadCutsint✅差切次数
FullCombobool✅是否全连
Accuracyfloat✅精度百分比（0-100）
NPSfloat❌所选难度的 NPS
SongDurationint✅歌曲时长（秒）
数据来源：LevelCompletionResults 在关卡结束时由 Beat Saber 引擎提供， 我们通过 StandardLevelScenesTransitionSetupDataSO.didFinishEvent 回调获取。 当前代码已在 PlaySessionManager.StartLevel() 中注册了此回调。

2.4 ExerciseSummary — 运动数据汇总

聚合一次会话中所有歌曲的运动数据。

字段类型说明
TotalScoreint本次会话总得分
AverageAccuracyfloat平均精度（%）
TotalNotesHitint总击中音符数
TotalNotesMissedint总失误数
TotalComboint总连击数（所有歌曲累加）
FullComboCountint全连歌曲数量
BestRankstring最佳评级
HighestNPSfloat最高 NPS 歌曲
TotalCutsint总切击次数（概算）
ActiveMinutesint实际活动时间（去掉等待和加载）

2.5 PlayerProfile — 玩家档案（聚合数据）

汇总所有历史会话的统计数据，每次会话结束后更新。

字段类型说明
TotalSessionsint总会话数
TotalPlayTimeMinint总游戏时长（分钟）
TotalSongsPlayedint总播放歌曲数
TotalScorelong累积总得分
BestAccuracyfloat历史最佳精度
FullComboTotalint历史全连总数
HighestRankstring历史最佳评级
FavoritePlayliststring最常使用的播放列表名称
LastPlayedAtDateTime最后游戏时间
FirstPlayedAtDateTime首次游戏时间
DailyStreakint连续游戏天数
聚合方式：PlayerProfile 通过扫描 History 目录下的所有 SessionRecord JSON 文件来计算。 每次会话结束后，加载 profile.json → 累加最新会话数据 → 保存回 profile.json。 若 profile.json 不存在，则全量扫描 History 目录重建。

2.6 SessionSettingsSnapshot — 设置快照

记录本次会话使用的设置参数，方便回顾当时的选择。

字段类型说明
MinNPSfloatNPS 下限
MaxNPSfloatNPS 上限
NoFailEnabledbool是否启用 No Fail
HudEnabledbool是否启用 HUD
PlaylistCountint选中的播放列表数量
AvailableSongCountint可选歌曲总数（筛选前）
注意事项：SongResult 中的 Score、Rank 等字段依赖 Beat Saber 的 LevelCompletionResults。若玩家中途退出（如暂停后退出、游戏崩溃）， 该歌曲的 SongResult 可能不完整。此时 Failed 标志应设为 true， 记录已获取到的部分数据（歌曲名、难度），其余字段使用默认值。

3 存储方案

3.1 存储路径

Beat Saber/
└── UserData/
    └── RandomPlaylistMod/          ← 模组专用数据目录
        ├── History/                ← 会话记录（一条一文件）
        │   ├── 20260623-143052-a1b2c3d4.json
        │   ├── 20260624-091530-e5f6g7h8.json
        │   └── ...
        ├── profile.json            ← 玩家聚合档案
        └── settings.json           ← （可选）模组设置持久化
路径规范：Beat Saber 模组的标准数据存储位置是 UserData/模组名/。 通过 IPA.Utilities.UnityGame.UserDataPath 获取 UserData 目录的绝对路径， 然后拼接 RandomPlaylistMod 子目录。

3.3 JSON 序列化

使用 Newtonsoft.Json（由 BSIPA 提供，项目已有依赖）进行序列化。

// 写入示例
var json = JsonConvert.SerializeObject(record, Formatting.Indented);
File.WriteAllText(filePath, json, Encoding.UTF8);

// 读取示例
var json = File.ReadAllText(filePath);
var record = JsonConvert.DeserializeObject<SessionRecord>(json);

// 配置：驼峰命名 + 忽略 null
var settings = new JsonSerializerSettings {
    ContractResolver = new CamelCasePropertyNamesContractResolver(),
    NullValueHandling = NullValueHandling.Ignore,
    DateTimeZoneHandling = DateTimeZoneHandling.Local
};

3.4 数据管理策略

策略说明
自动清理保留最近 90 天的记录，超出自动删除（可配置）
启动检查模组初始化时检查 History 目录是否存在，不存在则创建
异常保护写入失败时记录日志，不抛异常影响游戏
原子写入先写临时文件，成功后再 rename 为正式文件，防止写入中断导致数据损坏

4 持久化流程

4.1 核心类设计：HistoryManager

/// <summary>
/// 负责所有数据的持久化读写操作。
/// 在 AppInstaller 中注册为 AsSingle()，全局可访问。
/// </summary>
public class HistoryManager
{
    private string _dataPath;       // UserData/RandomPlaylistMod/
    private string _historyPath;    // UserData/RandomPlaylistMod/History/
    private string _profilePath;    // UserData/RandomPlaylistMod/profile.json

    // ---- 会话记录 ----
    void SaveSession(SessionRecord record);           // 保存一条会话记录
    List<SessionRecord> LoadAllSessions();             // 加载所有历史会话
    List<SessionRecord> LoadRecentSessions(int count); // 加载最近 N 条
    SessionRecord LoadSession(string sessionId);       // 按 ID 加载
    void DeleteSession(string sessionId);              // 删除指定会话

    // ---- 玩家档案 ----
    PlayerProfile LoadProfile();                       // 加载玩家档案
    void UpdateProfile(PlayerProfile profile);         // 更新玩家档案

    // ---- 模组设置 ----
    void SaveSettings(SessionSettings settings);       // 保存模组设置
    SessionSettings LoadSettings();                    // 加载模组设置

    // ---- 清理 ----
    void CleanOldRecords(int keepDays = 90);           // 清理旧记录
}

4.2 数据保存时机

会话启动 → 歌曲完成
(OnSongFinished) → 累加 SongResult
到内存缓存 → 会话结束
(EndSession) → 构建 SessionRecord
写入 JSON 文件 → 更新 PlayerProfile
写入 profile.json → 完成
关键设计：
  1. 会话进行中，SongResult 先存入内存列表（PlaySessionManager._currentResults）
  2. 歌曲失败或中途退出时，仍尝试保存已有的 SongResult（标记 Failed=true）
  3. 会话结束时一次性构建 SessionRecord 并写入 JSON
  4. JSON 写入在独立线程中执行（Task.Run），不阻塞 Unity 主线程
  5. PlayerProfile 的更新在 SessionRecord 写入成功后触发

4.3 现有代码修改点

文件修改内容
PlaySessionManager.cs 1) 新增字段 List<SongResult> _currentResults（内存缓存）
2) OnSongFinished() 中提取 LevelCompletionResults 构建 SongResult 并加入列表
3) EndSession() 中调用 HistoryManager.SaveSession()
Plugin.cs 在 AppInstaller 中注册 HistoryManager.AsSingle()
RandomPlaylistUI.cs （可选）Construct() 中调用 LoadSettings() 恢复上次设置

4.4 回调数据提取

当前 StartLevel() 中的回调需要增强，以捕获 LevelCompletionResults：

// 现有代码（PlaySessionManager.StartLevel）
_starter.didFinishEvent += (results, __) => {
    // results 类型：LevelCompletionResultsWrapper → LevelCompletionResults
    var songResult = new SongResult {
        SongName = level.songName,
        Author = level.levelAuthorName,
        LevelId = level.levelID,
        Difficulty = difficulty.ToString(),
        Score = results.levelCompletionResults.modifiedScore,
        MaxScore = results.levelCompletionResults.maxModifiedScore,
        Rank = results.levelCompletionResults.rank.ToString(),
        MaxCombo = results.levelCompletionResults.maxCombo,
        MissedNotes = results.levelCompletionResults.missedNotes,
        BadCuts = results.levelCompletionResults.badCuts,
        FullCombo = results.levelCompletionResults.fullCombo,
        Accuracy = CalculateAccuracy(results),
        // ... 其余字段
    };
    _currentResults.Add(songResult);
    OnSongFinished();
};

5 分享功能设计

5.1 定义：什么是「双次应用分享」

层级分享场景说明
第一层 游戏内会话总结 会话结束后，在菜单界面弹出一个总结面板，展示本次会话的核心数据
（打了多少歌、得分、精度、全连数等），支持截图保存
第二层 外部平台分享 将会话总结生成一张精美的图片（类似之前生成的小红书图片），
用户可保存图片后分享到 B站、小红书、Discord 等平台
「双次应用」解释：
  1. 第一次应用：游戏内数据持久化（历史记录查看、统计分析）
  2. 第二次应用：数据导出为可视化内容（分享卡片、社交传播）
同一份数据，两种使用场景 —— 个人回顾 + 社交分享。

5.2 分享内容设计

分享卡片包含信息：

区域内容说明
头部模组名称 + 版本号 + 日期品牌标识
核心数据游戏时长 / 歌曲数 / 总得分 / 全连数四大关键指标
详细数据精度 / 最高NPS / 最佳评级 / 失误数补充数据
歌单信息使用的播放列表名称展示歌曲来源
歌曲亮点最高分歌曲 + 全连歌曲列表个性化内容
底部模组下载链接 / 二维码引流入口

分享卡片样式（参考之前生成的小红书图片）：

  • 1080×1440 竖版布局
  • 紫色渐变背景（保持品牌一致性）
  • 数据以卡片形式展示，大号数字突出关键指标
  • 底部包含 GitHub 链接和二维码

5.3 分享交互流程

会话结束 → 生成 SessionRecord → 弹出总结面板
(SummaryView) → 用户选择
"生成分享图" → 生成分享图片
